# Unified_Treasury_Report

Единая консоль ETL-отчётов казначейства для BI.

## Установка

Минимальная версия Python — **3.9** (на рабочих машинах стоит 3.9/3.10).

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Учётные данные CBonds лежат в `CBonds_API/.env` (`CBONDS_LOGIN`, `CBONDS_PASSWORD`).

Пути к папкам с исходными Excel-файлами и результатами, шаблоны имён файлов и
константы отчётов настраиваются из самой консоли — пункт меню «Настройки»
(см. [раздел ниже](#настройки)). Править [config.py](config.py) руками больше
не нужно.

## Запуск

```bash
python console.py                              # интерактивное меню: выбрать отчёт -> параметры -> запуск
```

Без аргументов запускается интерактивное меню: выбор отчёта из красиво
оформленной таблицы, ввод параметров, спиннер во время загрузки с живыми
логами поверх него. Ctrl+C в любой момент (на выборе отчёта, при вводе
параметров, во время самой загрузки) отменяет только текущую операцию и
возвращает в меню — программа не закрывается.

Каждый отчёт можно запустить и напрямую аргументами командной строки.

## Настройки

Всё, что раньше правилось в `config.py`, теперь задаётся из консоли: пункт
«Настройки» в главном меню или подкоманда `settings`. Изменённые значения
ложатся в `settings.json` рядом с проектом (он в `.gitignore` — у каждого
пользователя свой), значения по умолчанию остаются в коде. Обновление проекта
настройки не затирает.

```bash
python console.py settings --list                        # все настройки и их значения
python console.py settings --list --group portfolio_dynamics   # один раздел
python console.py settings --set jupiter_root="/Volumes/Jupiter"
python console.py settings --set ovp_dir="/Volumes/Jupiter/data/OVP" chpd_dir="..."
python console.py settings --get ovp_dir                 # только значение — удобно в скриптах
python console.py settings --reset ovp_dir               # вернуть значение по умолчанию
python console.py settings --reset-all
python console.py settings --check                       # доступны ли все пути
python console.py settings --path                        # где лежит settings.json
```

Что настраивается: корень сетевого архива, папка логов, папка загрузок, по
каждому отчёту —
папка исходных файлов, папка (или файл) результатов, шаблон имени файла с датой
и формат этой даты; для «Ставок ОФЗ» — путь к `.env`, файл результата и глубина
истории; для «Динамики портфелей» — делитель объёмов, порог расхождения, сдвиг
сравнения по умолчанию, папки по датам и приёмка из загрузок.

**Корень и производные папки.** Пока папка конкретного отчёта не задана явно,
она отсчитывается от корня архива: сменили `jupiter_root` — переехали все
`data/<Отчёт>` и `output/<Отчёт>` сразу. Заданная явно папка от корня больше не
зависит. В интерактивном редакторе «-» вместо значения возвращает настройку к
значению по умолчанию, жёлтым подсвечены изменённые.

**Папки по датам.** Чтобы в папке с исходными файлами не копился «зоопарк»
выгрузок за все даты сразу, отчёт может искать их в подпапках вида `2026-09-18`.
Папки на несколько дней вперёд создаются разом — «д» в редакторе настроек или:

```bash
python console.py settings --make-folders portfolio-dynamics --days 14
python console.py settings --make-folders portfolio-dynamics --days 14 --include-weekends
```

По умолчанию создаются только рабочие дни, начиная с сегодня; повторный запуск
ничего не портит — уже существующие папки не трогаются. Формат имени папки
задаётся настройкой `date_folder_format` («Общее»).

**Проверка путей** (`--check` или «п» в редакторе) показывает по каждому пути,
доступен ли он и сколько файлов в нём нашлось по маске источника. Отсутствие
папки-источника — ошибка (обычно не примонтирован сетевой диск или опечатка);
отсутствие выходной папки — норма, она создастся при первом запуске.

**Некорректные значения не принимаются**: регулярка без ровно одной группы
(иначе отчёт находит файл, но не дату в его имени), формат даты, из которого
дата не разбирается обратно, ноль или отрицательное число там, где нужно
положительное. Несуществующий путь при этом сохраняется с предупреждением —
сетевой диск может быть просто не примонтирован прямо сейчас.

**Логин и пароль CBonds в настройках не хранятся** — они остаются в
`CBonds_API/.env`, закрытом `.gitignore`. Настройкой сделан только путь к этому
файлу: `settings.json` лежит рядом с кодом открытым текстом, и складывать в него
секреты означало бы ухудшить их хранение.

### Ставки ОФЗ (CBonds API)

Три взаимоисключающих режима периода:

```bash
python console.py ofz-rates --date 2026-07-01 --lookback-days 30    # одна дата + история назад (по умолчанию)
python console.py ofz-rates --date-from 2026-06-01 --date-to 2026-06-10   # интервал дат
python console.py ofz-rates --dates 2026-06-01,2026-06-15,2026-07-01      # список конкретных (не обязательно смежных) дат
```

Если корпоративный файрвол не пропускает запросы из Python, тот же отчёт можно
собрать прямо в Excel — запросы уйдут из процесса Excel (нужен Excel под Windows): см.
[excel_ofz/README.md](excel_ofz/README.md).

### Файловые отчёты (ОВП, Структура баланса, ЧПД, NIM, Динамика портфелей)

```bash
python console.py balance-struct --date 2026-06-18            # один файл на дату
python console.py balance-struct --dates 2026-06-18,2026-06-25 --combine   # несколько файлов -> ОДИН csv
python console.py chpd --inputs "a.xlsx" "b.xlsx"              # несколько файлов -> отдельные csv (по умолчанию)
python console.py ovp --inputs report1.xlsx report2.xlsx --combine
python console.py transfert-stavka --short-date 2026-03-17 --long-date 2026-04-30
python console.py portfolio-dynamics --t0-date 2026-09-01 --t7-date 2026-08-25
```

Без `--date`/`--input`/`--inputs`/`--dates` файловые отчёты сами находят
самый свежий файл в папке источника (см. [«Настройки»](#настройки)).

В интерактивном режиме консоль показывает 5-10 последних найденных файлов
(чтобы не засорять экран более старыми) и позволяет выбрать сразу несколько:
номерами из списка, датами (YYYY-MM-DD, в том числе за пределами показанных
5-10) или именами файлов через запятую — можно смешивать. По умолчанию
каждый выбранный файл сохраняется в свой CSV; если выбрано больше одного
файла, консоль спросит, объединить ли всё в один CSV.

У ОВП нет типового имени файла с датой (в отличие от остальных), поэтому его
`SourceConfig` в `config.py` сортирует файлы по дате изменения (mtime), а не
по дате из имени — во всём остальном (топ-N, мультивыбор, batch) работает
так же, как у остальных отчётов.

Если папка из настроек недоступна (не примонтирован сетевой диск,
опечатка в пути) или в ней не нашлось ни одного подходящего файла —
консоль не падает с ошибкой, а предлагает вписать путь(и) к файлу вручную.

«Трансфертные ставки» — особый случай: отчёту нужны ДВА файла за раз
(короткие + длинные ставки), поэтому пакетный режим (несколько запусков за
один вызов) для него пока не реализован.

«Динамика портфелей» — тоже два файла за раз (срез T0 и срез T-7), и ещё две
особенности, которых нет ни у одного другого отчёта.

Во-первых, он отдаёт **.xlsx, а не CSV**: на выходе шаблон обмена схемы v3.0
(см. `_portfolio_dynamics_spec/CONTRACT.md`) — машинные листы `fact_type_daily`
и `fact_portfolio_snapshot`, ручные `dim_portfolio` и `fact_limit`, витрины на
формулах, лист `checks` с 24 проверками и словарь данных `dict`. Имя файла —
`dinamika_portfeley_<дата T0>.xlsx`.

**Раскладка по папкам-датам.** Обе выгрузки за день кладутся в подпапку вида
`2026-09-18` внутри папки исходных файлов — и отчёт **без аргументов** сам
находит нужную: берёт самую свежую папку, *в которой есть файлы* (пустые,
созданные заранее, пропускаются), сам определяет, какой из двух файлов T0, а
какой T-7 — по дате самой выгрузки, а не по имени файла, — и кладёт результат
в `output`. Переименовывать и раскладывать в правильном порядке ничего не нужно.

**Приёмка из загрузок.** Носить файлы руками из «Загрузок» в `data/<дата>/` не
нужно: если в папке нужной даты срезов не хватает, отчёт сам находит их в папке
загрузок, раскладывает по папкам-датам и запускается. Посторонние файлы в
загрузках не трогаются — только те два, что нужны на выбранную дату.

Ищутся они **двумя способами**. Сначала по шаблону имени — это бесплатно.
Потом, если по имени не нашлось, по **содержимому** книги: выгрузку легко
переименовать (браузер дописывает «(1)», человек правит имя руками, система
однажды меняет формулировку), и привязка к одному шаблону означала бы, что файл
лежит прямо в загрузках, а отчёт его «не видит» без всяких объяснений. Признак
берётся строгий — и шапка нужной выгрузки, и дата в ней, — поэтому за срез
позиций не примут ни файл лимитов, ни чужой отчёт с диапазоном дат в заголовке.
Каждая такая находка пишется в лог с именем файла и разобранной датой, а
`--diagnose` показывает её отдельной пометкой «опознан по содержимому».

По содержимому проверяются только книги, не подошедшие по имени, начиная с
самых свежих и не больше сотни: в папке загрузок бывают тысячи файлов.

При запуске отчёт спрашивает отчётную дату и показывает, на какие даты данные
есть и откуда возьмутся — из папки или из загрузок; Enter выбирает последнюю.

**Первый запуск.** Пути к папкам по умолчанию указывают на сетевой архив
Jupiter — пока они не заданы, отчёту неоткуда брать данные и некуда их класть:

```bash
python console.py settings --set portfolio_dynamics_dir="<папка исходных файлов>" \
    portfolio_dynamics_output_dir="<папка результатов>" downloads_dir="<папка загрузок>"
python console.py portfolio-dynamics --diagnose   # что отчёт видит и почему не находит
```

`--diagnose` ничего не считает: показывает пути и существуют ли они, папки-даты
с числом файлов **и датами лежащих в них срезов** (дата папки и дата файла —
разные вещи: в папке 18.09 лежит и срез за 11.09), все .xlsx в загрузках с
пометкой «подошёл по имени / опознан по содержимому / не подошёл» и итоговый
список дат с указанием, откуда возьмётся каждый файл. Это первое, что стоит
запустить, если отчёт говорит, что данных нет.

Сами папки-даты создавать заранее не обязательно — приёмка создаст нужную сама.
Заранее их создают, чтобы было куда складывать выгрузки руками.

```bash
python console.py portfolio-dynamics                      # последняя доступная дата
python console.py portfolio-dynamics --date 2026-09-18     # конкретная дата (+ приёмка из загрузок)
python console.py portfolio-dynamics --folder 2026-09-18   # конкретная папка (дата, имя или путь)
python console.py portfolio-dynamics --no-import           # не заглядывать в загрузки
```

**Каждый срез кладётся дважды** — в папку отчётной даты (где он нужен как часть
пары) и в папку своей собственной даты. Иначе файл за 11.09, попавший в
`2026-09-18/` как T-7, остался бы в единственном экземпляре, и отчёт на 11.09
потом было бы не собрать без повторной выгрузки. После двух еженедельных
запусков раскладка выглядит так:

```
data/PortfolioDynamics/
├── 2026-09-04/   [04.09]                 ← дубль: сам себе T0
├── 2026-09-11/   [04.09] + [11.09]       ← полная пара
└── 2026-09-18/   [11.09] + [18.09]       ← полная пара
```

Любую из этих дат можно пересобрать задним числом, ничего не выкачивая заново.
Стоит это ровно одного лишнего файла на запуск; выключается настройкой
«Дублировать срез в папку его даты».

**Пара собирается по ТРЁМ местам сразу**: папка отчётной даты, другие папки-даты
и загрузки. Это обязательное следствие раскладки выше: приёмка сама разносит
срезы по папкам их дат и вычищает загрузки, поэтому через неделю работы T-7
существует единственным экземпляром в своей папке. Если искать пару только в
папке отчётной даты и в загрузках, свежая выгрузка перестаёт собираться — отчёт
объявляет, что файла нет, стоя ровно в той папке, куда сам его и положил.

Приоритет при равной дате: файл из папки отчётной даты, затем из другой
папки-даты, затем из загрузок. Из чужой папки-даты файл **копируется**, а не
переносится: там он единственный экземпляр отчёта на свою дату, и «перенести»
значило бы чинить сегодняшний отчёт, ломая прошлый. В логе видно, откуда взят
каждый срез.

Папка загрузок задаётся настройкой `downloads_dir` («Общее», по умолчанию
`~/Downloads`; на русской Windows она может называться «Загрузки»). По умолчанию
файлы **переносятся** — из загрузок исчезают, чтобы те не копили мусор;
настройка «Переносить, а не копировать» переключает на копирование. Ничего не
удаляется ни в том, ни в другом случае. Вся приёмка целиком выключается
настройкой «Забирать выгрузки из загрузок».

Папки создаются заранее пачкой: `python console.py settings --make-folders
portfolio-dynamics --days 14` (или «Настройки» → «д»). Если имя папки и дата
внутри выгрузки разошлись — в лог уйдёт предупреждение, а отчёт будет построен
на дату из выгрузки.

Плоская раскладка (все файлы в одной папке) продолжает работать: её можно
оставить, выключив настройку «Складывать выгрузки в папки по датам», а при
включённой настройке обе раскладки сканируются одновременно — переходить можно
постепенно. Без папок-дат отчёт берёт два самых свежих файла: новее — T0,
предыдущий — T-7.

**Лимиты приходят третьим файлом.** Выгрузка «Состояние лимитов на дату
21_09_2026 - Результат.xlsx» на ОТЧЁТНУЮ дату забирается из загрузок вместе со
срезами и ложится в ту же папку-дату. Из неё берутся колонки «Тип лимита» и
«Лимит сверху» (шапка ищется по содержимому, а не по номеру строки), значения
переводятся из рублей в млн, а границы зон считаются фиксированными процентами
от лимита (таблица зашита в коде, настройкой не является):

| Тип | Зелёная | Жёлтая | Красная |
|---|---|---|---|
| TSS (в файле «Облигации») | 78,08 % | 85,09 % | 95,10 % |
| AFS | 90,32 % | 93,55 % | 96,77 % |
| HTM | 89,29 % | 92,86 % | 96,43 % |
| HTM_KUAP | 78,00 % | 85,00 % | 95,00 % |

Два правила разбора, которых нет в других выгрузках: тип **AFS встречается
дважды** — берётся строка с бо́льшим лимитом; торговый портфель называется в
этом файле **«Облигации»** — соответствие задаётся настройкой
`portfolio_dynamics_limit_aliases` (по умолчанию `Облигации=TSS`). Строки, не
сводящиеся ни к одному типу портфелей, в `fact_limit` не попадают и
перечисляются в логе.

**«Остаток лимита сверху» пишется в `fact_limit` колонкой `limit_remaining`.**
Это не расчёт отчёта, а вторая, независимая величина из самой системы лимитов,
поэтому её нельзя ни восстановить, ни пересчитать — либо она записана, либо
потеряна. Формулы витрин её не используют; она нужна для сверки: `limit_amount`
минус остаток должно сходиться с объёмом типа в `fact_type_daily`. Расхождение
свыше 0,5 % отчёт пишет в лог отдельной строкой по каждому типу.

Колонка дописана **последней**, после `updated_by`: формулы витрин и `checks`
адресуют лист буквами (`$B` — лимит, `$C..$E` — границы зон), и вставка в
середину сдвинула бы их все. В выпуске, сделанном до её появления, колонки нет —
она дозаполняется пустой, и вчерашний файл читается как раньше.

Остаток не пишется в двух случаях: тип не пришёл в файле (тогда строка целиком
переносится из предыдущего выпуска) и лимит типа был **поделён на подлимиты** —
остаток в файле относится к совокупному лимиту, и рядом с долей от него он
означал бы неправду. Обе ситуации видны в логе.

Файла лимитов нет — не ошибка: лимиты переносятся из предыдущего выпуска, как и
раньше, с предупреждением в лог. Тип, которого нет в файле, тоже сохраняет
прежний лимит — один неполный файл не обнулит уже согласованное. Изменение
лимита относительно прошлого выпуска пишется в лог отдельной строкой: лист
`fact_limit` человек считает своим, и молча переписывать его нельзя.

**Лимит в выгрузке — СОВОКУПНЫЙ, и типы бывают вложенными.** Лимит `AFS`
ограничивает все портфели AFS вместе; лимит `HTM` ограничивает `HTM` и
`HTM_KUAP` **вместе**, при том что у `HTM_KUAP` есть ещё и свой подлимит.
Вложенность задаётся настройкой `portfolio_dynamics_type_parents` (по умолчанию
`HTM_KUAP=HTM`) и означает три вещи:

- объём объемлющего типа в `fact_type_daily` считается вместе с вложенными:
  `volume(HTM) = HTM + HTM_KUAP` — иначе светофор HTM занижал бы использование
  и не показал бы превышение общего лимита;
- у портфелей вложенного типа снимается `include_in_total`, чтобы ИТОГО по
  банку не сложило КУАП дважды (это тот самый случай из CONTRACT.md, п. 8.2);
  каждое снятие флага пишется в лог — колонка ручная, и молча её трогать нельзя;
- «Сумма по портфелям» в `view_by_type` у объемлющего типа тоже складывается с
  вложенными, иначе `CHK_16` показывал бы расхождение грейнов там, где его нет.

**Сколько отдано вложенному типу — настройка.** Выгрузка даёт только общее
число (скажем, `HTM = 900`); как поделить его между КУАП и остальным HTM,
решает казначейство. Задаётся настройкой `portfolio_dynamics_nested_limits`:

```bash
python console.py settings --set portfolio_dynamics_nested_limits="HTM_KUAP=100"
```

Сумма в млн RUB. При `HTM = 900` и `HTM_KUAP = 100` получится: КУАП — лимит
100, весь остальной HTM — 800. Тогда объёмы сравниваются **раздельно**
(`volume(HTM)` без КУАП), сложение не нужно, и `include_in_total` остаётся у
всех: пересечения нет. Подлимит из настройки перебивает строку этого типа в
файле лимитов, если она там есть.

Подлимит **не задан** — работает режим из предыдущего абзаца: объём вложенного
типа складывается с объемлющим и сравнивается с общим лимитом целиком. Так
безопаснее — превышение общего лимита не потеряется, пока доли не согласованы.
В обоих режимах у вложенного типа своя строка, свой светофор и свои проценты
зон.

**Портфели, которых нет в выгрузке**, ведутся вручную: «Настройки» → «р»
(добавить, изменить, удалить). Диалог спрашивает код, название, тип, объём в
млн RUB и дюрацию. Такой портфель попадает и в справочник `dim_portfolio`, и в
срез, и в объём своего типа — иначе он выпал бы из светофора. Объём T-7
берётся из предыдущего выпуска, поэтому правка объёма видна в отчёте как
настоящее изменение, а не как ноль. Если такой код вдруг появится в выгрузке,
победит выгрузка, а в лог уйдёт предупреждение. Дюрацию можно не указывать, но
тогда `CHK_14` («пустая текущая дюрация в срезе») покажет FAIL.

**Разметка портфелей по типам** — главный источник это файл
`portfolio_types.json` (по умолчанию рядом с `settings.json`, путь — настройка
`portfolio_dynamics_types_file`; открыть на правку: «Настройки» → «т»):

```json
{
  "TSS":      ["OFZ_PD", "OFZ_PK", "OFZ_CNY"],
  "AFS":      ["AFS_*"],
  "HTM":      ["OFZ_HTM", "HTM_ALCO"],
  "HTM_KUAP": ["HTM_KUAP_CORE"],
  "_не_размечены": {"NEW_CODE": "AFS?"}
}
```

Ключ — тип, значение — коды портфелей; можно маски `*`/`?`, точный код важнее
маски. Что указано в файле, то и тип — поверх правил и настроек ниже. Типов в
отчёте ровно столько, сколько ключей в файле (TSS, AFS, HTM и подтип
HTM_KUAP): угаданное по коду «OFZ» типом не становится, а такие типы из
лимитов и истории прошлого выпуска убираются с предупреждением. Файла нет —
отчёт создаёт его сам; портфели без явной разметки он дописывает в
`_не_размечены` с угаданным типом — остаётся перенести код в нужный список.
Файл не попадает ни в git, ни в архив `export_project.sh`, чтобы обновление
кода не затёрло разметку.

Портфели, которых в файле нет, размечаются по правилам от частного к общему:

1. точечное исключение из настройки `portfolio_dynamics_portfolio_types`
   (`OFZ_CNY_SPEC=HTM`) — перебивает всё, в том числе уже проставленный тип в
   `dim_portfolio`, с записью в лог;
2. самый длинный известный тип, которым код **начинается**: `HTM_KUAP_CORE` →
   `HTM_KUAP`, `AFS_OFZ_PD` → `AFS`. Это должно идти раньше правил по
   подстроке, иначе правило «HTM» перехватывало бы КУАП;
3. правила по **вхождению** подстроки — настройка
   `portfolio_dynamics_type_rules`, по умолчанию
   `HTM=HTM, OFZ_PD=TSS, OFZ_PK=TSS, OFZ_CNY=TSS`: `OFZ_HTM` → `HTM`,
   `OFZ_PD`/`OFZ_PK`/`OFZ_CNY` → торговый. Срабатывает первое подходящее, так
   что порядок в настройке — это приоритет;
4. если ничего не подошло — префикс до первого `_`.

Правила применяются **ко всем строкам справочника, а не только к новым**:
`dim_portfolio` переносится из предыдущего выпуска целиком, и без пересчёта
портфель, размеченный до появления правила, так и остался бы с прежним типом —
правило есть, а разметка «не чинится». Каждое изменение пишется в лог. Тип, не
сводящийся ни к одному известному, не проставляется: странный код не должен
затирать уже верную разметку мусором.

Четыре согласованных типа (`AFS`, `HTM`, `HTM_KUAP`, `TSS`) известны всегда,
даже когда файла лимитов нет. Торговый тип в настройках и в старых файлах можно
писать и `TSS`, и прежним написанием `TTS` — отчёт приводит его к `TSS` сам.

**Накопленную историю можно подтянуть из отчёта старого формата.** Лист
`fact_type_daily` — это и есть «объёмы по всем группам»: дата, тип портфеля,
суммарный объём за день. У первого выпуска он пуст (история копится по одной
дате за запуск), но если она уже ведётся в прежнем отчёте, её переносят оттуда:

Три способа, любой на выбор — «Настройки» → **«и»**, аргумент командной строки
или настройка напрямую:

```bash
python console.py portfolio-dynamics --history "старый отчёт динамики.xlsx"
python console.py settings --set portfolio_dynamics_history_file="/путь/к/файлу.xlsx"
```

Путь помнить не обязательно: и «Настройки» → «и», и вопрос при первом выпуске
сами **ищут подходящие книги** в папке загрузок, папке исходных файлов и папке
выгрузки, показывают их списком с перечнем листов и дают выбрать номером. Имя у
старого отчёта произвольное, поэтому поиск идёт по содержимому — по наличию
листов «Динамика <ТИП>»; открывать книгу ради этого не требуется, имена листов
лежат в её оглавлении. Выбранный файл тут же разбирается, и на экран выводится,
сколько строк, каких типов и за какой период прочиталось. `--diagnose` тоже
показывает найденных кандидатов, если импорт ещё не настроен.

Старый формат — по листу на тип: «Динамика AFS», «Динамика HTM», «Динамика
TSS», в каждом колонки «Дата», «Текущий объём», «Изменение». Читаются только
первые две: изменение отчёт считает сам. Объём в старом файле уже суммарный по
типу за день — тот же грейн, что и в `fact_type_daily`, поэтому перенос идёт
один в один, только рубли переводятся в млн (`portfolio_dynamics_history_scale`).
Если лист назван не так, как называется тип, соответствие задаётся настройкой
`portfolio_dynamics_history_aliases` (вида «имя листа=тип»); написание **TSS**
отчёт понимает и без псевдонимов, а старое **TTS** приводит к нему сам.

Импорт **только дополняет**: пара (дата, тип), уже накопленная своими
запусками, не перезаписывается никогда, поэтому повторный запуск с тем же
файлом ничего не портит. Если единицы разойдутся с сегодняшними объёмами на
порядки, отчёт предупредит об этом в логе. В интерактивном режиме про историю
спрашивают только на первом выпуске — дальше она живёт в предыдущем файле.

Во-вторых, он работает **инкрементально: предыдущий выпуск отчёта является
входом для следующего**. Входные выгрузки дают только два среза, а истории
объёмов по типам (лист `fact_type_daily`), лимитов и заметок в них нет — всё
это накапливается в самом файле. Каждый запуск читает предыдущий выпуск
(по умолчанию — самый свежий xlsx в выходной папке, либо явный путь через
`--previous`), дописывает в историю одну дату T0 (повторный прогон за ту же
дату ЗАМЕНЯЕТ свои строки, а не задваивает их), переносит `fact_limit` и
`dim_portfolio` как есть и возвращает `note_text` на место по `portfolio_code`.
Первый запуск, когда предыдущего файла ещё нет, требует явного `--bootstrap`:
история заводится с одной даты, лимиты — нулевые, и их надо заполнить руками.

```bash
python console.py portfolio-dynamics --t0-input a.xlsx --t7-input b.xlsx
python console.py portfolio-dynamics --t0-input a.xlsx --t7-input b.xlsx --previous prev.xlsx
python console.py portfolio-dynamics --t0-input a.xlsx --t7-input b.xlsx --bootstrap
```

Дата отчёта берётся из ВТОРОЙ даты в имени файла выгрузки
(`Позиция за период   18.09.2026  -  18.09.2026   - SECURITIES.xlsx` -> 2026-09-18);
если файл переименовали, та же строка ищется в шапке листа. Шаблон имени терпим
к оформлению: квадратные скобки вокруг дат необязательны (в имени файла их нет,
а в шапке листа есть), число пробелов любое. Если выгрузка начнёт называть файлы
иначе, шаблон правится без кода — настройка `portfolio_dynamics_regex`, а
`--diagnose` показывает по каждому файлу, подошёл он под шаблон или нет. Объёмы выгрузка
отдаёт в рублях, а схема требует млн RUB — масштаб задаётся константой
`PORTFOLIO_DYNAMICS_VALUE_SCALE` в `config.py`.

## Структура проекта

- `CBonds_API/` — перенесённая библиотека-клиент CBonds JSON API (общая для всех отчётов).
- `common/` — общие утилиты, переиспользуемые разными отчётами:
  - `ui.py` — оформление консоли (rich): меню, спиннер, стилизованные сообщения.
  - `logging_utils.py` — единое логирование (RichHandler в консоль + `logs/<report>.log`).
  - `file_discovery.py` — поиск входных файлов по дате, зашитой в имени файла (топ-N дат / список дат / имя файла, одиночный и множественный выбор).
  - `batch.py` — запуск ETL по списку файлов: раздельные CSV (по умолчанию) или один объединённый (`--combine`).
  - `settings.py` — реестр настроек (значения по умолчанию, разбор и проверка значений) и их хранение в `settings.json`. Без rich и без импорта `config` — его импортирует сам `config`.
  - `settings_ui.py` — пункт меню «Настройки»: экраны редактора и неинтерактивный режим подкоманды `settings`.
- `config.py` — пути к папкам с исходными данными и результатами (`SourceConfig` на каждый источник). Собирается из слоя настроек; руками не правится.
- `settings.json` — изменённые пользователем настройки (создаётся при первой правке, в репозиторий не коммитится).
- `reports/<report_slug>/` — код конкретного отчёта: `etl.py` (получение и преобразование данных) + `report.py` (обёртка для консоли: CLI-аргументы и интерактивный режим).
  - `reports/ofz_rates/` — «Ставки ОФЗ» (кривая доходности ОФЗ из CBonds API).
  - `reports/ovp/` — «ОВП» (конвертация Excel-отчёта «Открытая валютная позиция» в CSV).
  - `reports/balance_struct/` — «Структура баланса» (разбор Excel «ПФ_ДД_ММ_ГГГГ» по иерархии активов/пассивов).
  - `reports/chpd/` — «ЧПД» (разбор Excel «ЧПД YYYY MM DD», лист Table).
  - `reports/nim/` — «NIM» (разбор Excel «NIM_YYYY_MM» по текстовым маркерам).
  - `reports/transfert_stavka/` — «Трансфертные ставки» (два файла: короткие + длинные сроки).
  - `reports/portfolio_dynamics/` — «Динамика портфелей» (два среза выгрузки позиций -> xlsx схемы v3.0; единственный отчёт с xlsx на выходе и инкрементальным накоплением истории). Разбит на три модуля: `etl.py` (разбор выгрузок и слияние с предыдущим выпуском), `workbook.py` (сборка xlsx: листы, формулы, форматирование, валидация, checks), `report.py` (CLI и интерактив), `inbox.py` (поиск выгрузок в папке загрузок и раскладка их по папкам-датам), `limits.py` (разбор выгрузки «Состояние лимитов» и сборка листа `fact_limit`), `history.py` (импорт накопленной истории из отчёта старого формата).
- `excel_ofz/` — автономная Excel-версия отчёта «Ставки ОФЗ» (VBA ходит в CBonds API напрямую, без Python).
- `console.py` — точка входа: реестр отчётов + меню/CLI.
- `output/<report_slug>/` — результаты запусков (для файловых отчётов путь берётся из `config.py`).
- `logs/` — логи запусков (по одному файлу на отчёт).

## Тесты

```bash
python -m unittest tests.test_ovp_etl tests.test_portfolio_dynamics_etl \
    tests.test_settings tests.test_date_folders tests.test_inbox \
    tests.test_limits tests.test_history tests.test_manual_portfolios \
    tests.test_workbook_formulas tests.test_python_compatibility
```

`tests/test_python_compatibility.py` проверяет, что весь код компилируется на
Python 3.9. Это не паранойя: синтаксис, появившийся позже, интерпретатор
разработчика принимает молча, а у пользователя падает сразу на импорте консоли.
Нужен `pip install parso` — парсер с грамматикой конкретной версии; без него
тест пропускается. Ни `ast.parse(feature_version=...)`, ни `vermin` такие
ошибки не ловят (проверено). Полная гарантия — прогнать набор настоящим
интерпретатором 3.9:

```bash
uv venv --python 3.9 py39 && uv pip install --python py39/bin/python -r requirements.txt
py39/bin/python -m unittest tests.test_portfolio_dynamics_etl ...
```

`tests/test_workbook_formulas.py` проверяет выходной .xlsx на двух уровнях.
Структурный работает всегда: ссылки формул ведут на существующие листы и
именованные диапазоны, функции — только уровня Excel 2007, ref умных таблиц
совпадает с данными. Вычислительный требует пакета `formulas`
(`pip install formulas`, в requirements его нет намеренно — зависимость тяжёлая
и нужна только для проверки): книга считается целиком, статусы листа `checks`
сверяются с тем, что посчитал питон, и проверяется, что ни одна ячейка не даёт
ошибку Excel. Без этого пакета вычислительные тесты помечаются как skipped.

## Добавление нового отчёта

1. Создать `reports/<slug>/etl.py` с получением и преобразованием данных.
2. Если у отчёта есть входные файлы с датой в имени — добавить `SourceConfig` в `config.py` и использовать `common.file_discovery` для поиска файла.
3. Создать `reports/<slug>/report.py` с классом, реализующим `reports.base.Report`.
4. Зарегистрировать отчёт в списке `REPORTS` в `console.py`.
