# Контракт данных: портфельные лимиты и динамика (схема v3.0)

Файл `portfolio_limits_template.xlsx` — промежуточный слой между ручным вводом казначейства и BI.
Все суммы — **млн RUB**.

**Что изменилось относительно v2.0**

- Лист `dim_type` удалён. Реестром допустимых типов служит `fact_limit` — там теперь ровно одна строка на тип.
- `dim_portfolio`: добавлен `include_in_total`, убран `is_active`.
- `fact_limit`: грейн изменён с портфеля на **тип**. Лимит — это ограничение на суммарный объём всех портфелей типа.
- `fact_portfolio_snapshot`: добавлена колонка `note_text`.
- Лист `ref_note` удалён — заметки переехали в срез.
- `view_monitor` заканчивается колонкой «Лимит типа». Утилизация, зона и свободный лимит переехали в `view_by_type`, где лимит и объём лежат на одном грейне.

---

## 1. Три грейна, каждый со своим источником

| Таблица | Грейн | Что в ней | Обновление |
|---|---|---|---|
| `fact_limit` | `portfolio_type` | Лимит и границы зон на **суммарный объём типа** | вручную |
| `fact_type_daily` | `(business_date, portfolio_type)` | История объёмов по типам с 01.01.2026 | дозапись свежих дат |
| `fact_portfolio_snapshot` | `portfolio_code`, одна дата на лист | Объём T0, объём T-7, дюрации, заметка | полная перезапись |
| `dim_portfolio` | `portfolio_code` | Справочник портфелей и привязка к типу | вручную |

Лимит и объём типа лежат на одном грейне — поэтому светофор считается корректно и живёт на `view_by_type`. По отдельному портфелю утилизация не определена: лимита на портфель не существует. В `view_monitor` колонка «Лимит типа» показывает лимит того типа, к которому портфель относится, — как справка, а не как база для сравнения.

Ежедневная история по детальным портфелям не хранится: её выгрузка потребовала бы запроса на каждый день за весь период. Прямое следствие — **`volume_t7` в срезе это входные данные, а не вычисляемая величина**. Колонка приходит из выгрузки, `CHK_13` не даёт молча загрузить срез без неё, иначе дельты по портфелям тихо обнулятся. Сдвиг, с которым выгрузка считает `volume_t7`, должен совпадать с `view_monitor!D3` — файл это не проверит, второй точки для сверки нет.

`fact_limit` выполняет двойную роль: держит лимиты и служит реестром типов. Выпадающие списки в `dim_portfolio.portfolio_type` и `fact_type_daily.portfolio_type` берут значения оттуда, `CHK_07` и `CHK_17` следят за целостностью в обе стороны. Новый тип заводится строкой в `fact_limit` — она же его и открывает.

## 2. Заметки живут в срезе — единственное место, требующее внимания в коде

`note_text` — ручная колонка на машинном листе. Лист перезаписывается целиком, поэтому загрузчик **обязан** вычитать заметки перед перезаписью и вернуть их на место по `portfolio_code`:

```python
old = pd.read_excel(f, sheet_name="fact_portfolio_snapshot")[["portfolio_code", "note_text"]]
new = new.merge(old, on="portfolio_code", how="left")   # заметки переживают загрузку
```

Шапка этой колонки помечена жёлтым посреди синего листа именно как напоминание. `CHK_15` считает портфели без заметки — если их число внезапно выросло, скорее всего шаг пропустили.

Заметки теперь не версионируются: остаётся только текущий текст. Если понадобится история целей, это возврат к отдельной таблице с `is_current`.

---

## 3. Сверка двух источников

Сумма объёмов портфелей одного типа (срез) и объём этого типа за ту же дату (история) приходят из разных выгрузок. В `view_by_type` они стоят рядом — «Объём типа T0», «Сумма по портфелям», «Расхождение» в процентах. Порог 0.5%, контролирует `CHK_16`, ячейка краснеет при выходе за него.

Это единственное место, где два грейна встречаются, и единственное, где вылезет рассинхрон выгрузок. Смотреть на него стоит первым делом.

## 4. Разделение зон ответственности

| Цвет шапки | Листы / колонки | Кто пишет |
|---|---|---|
| Тёмно-синяя | `fact_type_daily`, `fact_portfolio_snapshot` | только код |
| Тёмно-жёлтая | `dim_portfolio`, `fact_limit`, колонка `note_text` | только человек |
| Зелёная | `view_monitor`, `view_by_type`, `checks`, `dict` | формулы, в BI не грузятся |

Цвет текста в ячейке: синий — введено руками, чёрный — формула, зелёный — ссылка на другой лист.
Единственные ячейки ручного ввода на витринах — жёлтые `view_monitor!B3` (отчётная дата) и `view_monitor!D3` (сдвиг сравнения, календарных дней).

## 5. Листы

### `dim_portfolio`
Грейн `portfolio_code`. Поля: `portfolio_name`, `portfolio_type` (FK на `fact_limit`), `include_in_total`, `is_limit_controlled`, `sort_order`.

`include_in_total` защищает итог по банку от двойного счёта: тип попадает в ИТОГО, если хотя бы один его портфель помечен `TRUE`.

### `fact_limit`
Грейн `portfolio_type`, одна строка на тип. Поля: `limit_amount`, `green_max_util`, `yellow_max_util`, `red_max_util`, `valid_from`, `updated_by`.

Границы зон — абсолютные суммы, монотонно возрастающие; сравнивается с ними **объём типа**:

```
объём типа ≤ green_max_util   → ЗЕЛЁНАЯ
объём типа ≤ yellow_max_util  → ЖЁЛТАЯ
объём типа ≤ red_max_util     → КРАСНАЯ
объём типа >  red_max_util    → ПРЕВЫШЕНИЕ
```

`red_max_util` обычно равен `limit_amount`. `CHK_20` проверяет монотонность, `CHK_21` — что красная граница не задрана выше лимита.

### `fact_type_daily`
Грейн `(business_date, portfolio_type)`, поле `volume_amount`. Детализации до портфелей здесь нет и быть не должно — валидация принимает только типы из `fact_limit`.

### `fact_portfolio_snapshot`
Грейн `portfolio_code`, дата одна на весь лист (колонка `business_date` дублируется в каждой строке как аудиторский след и сверяется с `view_monitor!B3` через `CHK_09`). Поля: `volume_t0`, `volume_t7`, `duration_current_yrs`, `duration_target_yrs`, `note_text`.

Если история по портфелям когда-нибудь понадобится, она накапливается здесь — добавлением `business_date` в первичный ключ и переходом с перезаписи на дозапись.

### `view_monitor`
Строка на портфель: код, название, тип, объём T0 и T-7, Δ и Δ%, дюрация текущая и целевая, гэп дюрации, лимит типа. Подсветка движения объёма более ±5%.

### `view_by_type`
Динамика типа из истории, сумма по портфелям из среза, расхождение, лимит, утилизация, зона со светофором, свободный лимит, строка ИТОГО по `include_in_total`.

### `checks` — 24 проверки
История типов: непустота, максимальная дата равна отчётной, строк на T0 и T-7 равно числу типов, нет отрицательных объёмов, нет типов вне `fact_limit`.
Срез: число строк равно числу портфелей, дата совпадает с отчётной, нет дублей и неизвестных кодов, заполнены `volume_t0`, `volume_t7`, дюрация; счётчик пустых заметок.
Сверка грейнов: расхождение в пределах 0.5%.
Лимиты: тип без лимита, дубли типа, лимит ≤ 0, монотонность зон, красная граница не выше лимита.
Сигналы: типы в красной зоне, превышения, утилизация выше 100%.

**Любой `FAIL` блокирует загрузку в BI.**

### `dict`
`table_name / column_name / ru_label / data_type / required / rule / description / grain / owner`. Контракт лежит внутри файла и читается кодом; `note_text` помечена владельцем «казначейство (ручная)».

## 6. Технические правила

1. Строка 1 каждого листа — технические заголовки `snake_case`. `pd.read_excel(f, sheet_name=...)` работает без аргументов.
2. Не смешивать грейны: в `fact_limit` и `fact_type_daily` — только типы, в `dim_portfolio` и `fact_portfolio_snapshot` — только портфели.
3. Никаких объединённых ячеек, пустых строк-разделителей и строк «Итого» внутри таблиц.
4. Даты — настоящие даты Excel. Числа — числа: без разделителей, без «млн» и знака валюты внутри ячейки.
5. Пустая ячейка = «нет данных». Никаких `н/д`, `—` и нулей вместо пропуска.
6. Умные таблицы (`tbl_dim_portfolio`, `tbl_fact_limit`, `tbl_fact_type_daily`, `tbl_fact_portfolio_snapshot`) расширяются сами.
7. Валидация на входе: списки кодов и типов, `TRUE/FALSE`, `>= 0` для сумм, тип «дата» для дат.
8. Именованные диапазоны `BUSINESS_DATE`, `LOOKBACK_DAYS`, `PORTFOLIO_CODES`, `PORTFOLIO_TYPES`.

## 7. Как это читается кодом

```python
import pandas as pd

f = "portfolio_limits.xlsx"
dim   = pd.read_excel(f, sheet_name="dim_portfolio")
limit = pd.read_excel(f, sheet_name="fact_limit")
hist  = pd.read_excel(f, sheet_name="fact_type_daily")
snap  = pd.read_excel(f, sheet_name="fact_portfolio_snapshot")
spec  = pd.read_excel(f, sheet_name="dict")   # контракт из самого файла

assert not hist.duplicated(["business_date", "portfolio_type"]).any()
assert not snap.portfolio_code.duplicated().any()
assert snap.business_date.nunique() == 1
assert not limit.portfolio_type.duplicated().any()

assert set(hist.portfolio_type) <= set(limit.portfolio_type)
assert set(dim.portfolio_type)  <= set(limit.portfolio_type)
assert set(snap.portfolio_code) <= set(dim.portfolio_code)

assert (limit.green_max_util < limit.yellow_max_util).all()
assert (limit.yellow_max_util < limit.red_max_util).all()

# светофор считается по объёму ТИПА
bd  = snap.business_date.iloc[0]
cur = hist[hist.business_date == bd].merge(limit, on="portfolio_type")
cur["zone"] = cur.apply(
    lambda x: "ЗЕЛЁНАЯ"    if x.volume_amount <= x.green_max_util  else
              "ЖЁЛТАЯ"     if x.volume_amount <= x.yellow_max_util else
              "КРАСНАЯ"    if x.volume_amount <= x.red_max_util    else
              "ПРЕВЫШЕНИЕ", axis=1)

# сверка двух грейнов
by_type = (snap.merge(dim[["portfolio_code", "portfolio_type"]], on="portfolio_code")
               .groupby("portfolio_type").volume_t0.sum())
ref = cur.set_index("portfolio_type").volume_amount
assert ((by_type / ref - 1).abs() < 0.005).all()
```

В BI это две таблицы фактов с общим измерением: `fact_type_daily` join `fact_limit` даёт динамику и светофор, `fact_portfolio_snapshot` join `dim_portfolio` даёт таблицу по портфелям. Сходятся через `dim_portfolio.portfolio_type`.

Обратная запись: `fact_type_daily` — дозапись строк за новые даты; `fact_portfolio_snapshot` — очистка ниже заголовка и запись заново **с сохранением `note_text`**; `view_monitor!B3` — обновить датой нового среза.

## 8. Что нужно подтвердить

1. **Полный перечень типов и портфелей.** В шаблоне 4 типа и 11 демонстрационных портфелей.
2. **Пересекается ли HTM_KUAP с HTM?** Сейчас `include_in_total = TRUE` у всех портфелей, итог по банку — простая сумма. Если КУАП входит в HTM, снять флаг у его портфелей.
3. **С каким сдвигом выгрузка считает `volume_t7`?** Должно совпадать с `view_monitor!D3`.
4. **`red_max_util` = `limit_amount`?** В шаблоне да.
5. **Что такое вторая колонка «Дюрация»** — целевая, лимитная или на T-7? Трактована как целевая.
6. **Нужна ли история заметок?** Сейчас хранится только текущий текст, предыдущие версии не сохраняются.

## 9. Дальнейшее развитие

`dim_portfolio`, `fact_limit`, `fact_type_daily`, `fact_portfolio_snapshot` переезжают в Postgres один в один, с теми же ключами. Excel остаётся формой ввода лимитов и заметок, витрины и проверки уходят в SQL. Разделение грейнов при переезде не меняется — оно продиктовано источниками, а не форматом файла.
